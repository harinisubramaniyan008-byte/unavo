TABLE: users

01 — Registration & Profile

One table, role field.

Store users in one table with a `role` field: `donor`, `NGO`, `volunteer`, `beneficiary`. Fields: name, phone, email, address, location (lat/long), password (hashed), role. Logic: signup form → validate inputs → hash password → insert into DB → login checks credentials → redirect based on role (donor dashboard, NGO dashboard, etc.).

TABLE: food_items

02 — Food Listing

Available → Expired via cron.

Table: `food_items` — donor_id, food_name, quantity, food_type (veg/non-veg/packaged), expiry_date/time, pickup_location, status (available/claimed/expired). Logic: donor fills a form → entry saved with status = "available" → a simple scheduled check (cron job or a script run periodically) flips status to "expired" once expiry_date has passed.

⏱️ Cron: every 60s checks expiry → flips to expired
NO ML

03 — Food Matching (basic)

Filter + Sort, not prediction.

Step 1: Pull all `food_items` where status = "available". Step 2: Filter by distance — compare beneficiary's location to each donor's location (simple distance formula, e.g. Haversine, or even just "same city/pincode" if you want to keep it simpler). Step 3: Sort results by two priorities: (a) soonest expiry first, (b) shortest distance first. Step 4: Show ranked list; they click "claim" → status changes to "claimed", linked to their user_id. That's it — no training data, no model. It's a query + sort.

LAT/LNG • OSM

04 — Location & Routing

Browser API + Haversine + Leaflet.

Store lat/long for every user (captured via browser geolocation API on signup, or manually entered address geocoded once using a free API like OpenStreetMap Nominatim). Distance calculation: use the Haversine formula (a standard math formula for distance between two lat/long points) — no external routing service needed for a basic version. Optional: embed a map (Google Maps or OpenStreetMap/Leaflet) to visually show donor and beneficiary pins.

05 — Notification Module

Bell icon + polling, no websockets.

Table: `notifications` — user_id, message, type (new_food/claim_confirmed/urgent), status (read/unread), timestamp. Trigger logic: New food listed nearby → insert a notification row for beneficiaries/NGOs in range. Food claimed → notify the donor. Expiry approaching (e.g. 2 hours left) → notify NGOs to prioritize pickup. Basic delivery: just show notifications inside the app (a bell icon + list). For "real-time," you can poll the database every X seconds from the frontend — you don't need websockets or push services for a college project.
