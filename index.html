UnavO ♻️ | 5 Module System

1. Registration & Profile Module

Table: users - role field: donor, NGO, volunteer, beneficiary | Fields: name, phone, email, address, location (lat/long), password (hashed), role
Logic: signup form → validate inputs → hash password → insert into DB → login checks credentials → redirect based on role

2. Food Listing Module

Table: food_items — donor_id, food_name, quantity, food_type (veg/non-veg/packaged), expiry_date/time, pickup_location, status (available/claimed/expired)
Logic: donor fills form → entry saved with status = "available" → scheduled check (cron job) flips to "expired" once expiry_date passed

3. Food Matching Module (basic, no ML)

This is just filtering + sorting, not prediction:
Step 1: Pull all food_items where status = "available".
Step 2: Filter by distance — compare beneficiary's location to each donor's location (Haversine, or same city/pincode simpler).
Step 3: Sort results by two priorities: (a) soonest expiry first, (b) shortest distance first.
Step 4: Show ranked list; they click "claim" → status changes to "claimed", linked to their user_id.
That's it — no training data, no model. It's a query + sort.

4. Location & Routing Module

Store lat/long for every user (captured via browser geolocation API on signup, or manually entered address geocoded once using free API like OpenStreetMap Nominatim).
Distance: use Haversine formula - no external routing needed for basic.
Optional: embed map (Google Maps or OpenStreetMap/Leaflet) to show donor and beneficiary pins.

5. Notification Module

Table: notifications — user_id, message, type (new_food/claim_confirmed/urgent), status (read/unread), timestamp.
Trigger logic:
- New food listed nearby → insert notification for beneficiaries/NGOs in range.
- Food claimed → notify the donor.
- Expiry approaching (e.g. 2 hours left) → notify NGOs to prioritize pickup.
Basic delivery: show inside app (bell icon + list). For "real-time," poll DB every X seconds - no websockets needed.
🔔 Bell Icon - 0 unread (polling every 5 sec)
Suggested build order: Registration → Food Listing → Matching → Location → Notifications, since each one depends on data/users previous module creates.
